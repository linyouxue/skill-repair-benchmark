### 034.jpg — date `2018-08-09` is wrong, amount `332.30` correct

Image evidence: the header prints `Date: 09/03/2018` with `Time: 08:49:00` immediately to the right, printed in a light dot-matrix style that smears the "3" glyph. Agent's own transcript in w0003 (a0009) explicitly recorded it as "`date=09/08/2018`" from its single OCR pass, so the pytesseract pass confused "`3`" → "`8`" inside the date string, producing the string `09/08/2018`.

The date extractor's first DD-MM-YYYY hit then becomes `09/08/2018` → `2018-08-09`. Root causes, in order:

1. Single OCR pass with no `--psm` sweep / preprocessing variants, even though the `image-ocr` Skill explicitly documents a "Multi-Pass OCR Strategy" and digit-friendly PSM modes. The Skill was never invoked (`n_skill_invocations=0`).
2. No cross-check that the parsed date is internally consistent (e.g., with a visible `Receipt #` or the time-of-day field, or with the Mar 2018 printing of adjacent GST-era receipts).
3. No ambiguity handling for Malaysian DD/MM vs ISO MM/DD when only one hit is taken; a second, conflicting hit elsewhere on the receipt would have caught the OCR error, but the extractor returns on the first regex match.

Uncertainty: I cannot see the intended gold here, but DD/MM/YYYY is consistent with every other Malaysian receipt in the batch and with the time-adjacent token on this receipt. The error pattern (month `08` vs day/time-adjacent `08`) is a classic Tesseract 3→8 confusion rather than a policy issue.

### 074.jpg — amount `702.00` wrong, date correct

Image evidence: receipt body shows `Subtotal : 102.00`, `Total Excl. of GST 96.23`, `Total Incl. of GST 102.00`, `Total Amt Rounded 102.00`, `Payment : 102.00`. Gold intent is the rounded grand total `102.00`.

Agent's own reconstruction (w0003 a0012) of the OCR for this file:
- `Subtotal : 102.00` → excluded by `SUBTOTAL`.
- `TolalEcl. of GST 96.23` → "Tolal" does not match `\bTOTAL\b`; this line is silently skipped. 96.23 happens to be the ex-GST subtotal, so missing it is fine.
- `Total inel. of GBT 702.00` → `\bTOTAL\b` matches; "GBT" (not "GST") evades the `TOTAL\s+(GST|TAX|SST)` exclusion, and "inel" evades the `Incl` heuristic. The last number on this line is `702.00` — OCR has flipped the leading `1` → `7` in `102.00`.
- `Toial Amt Rounded oO yo2.00` → "Toial" and "yo2.00" both fail word-boundary / 2-decimal regex, so the correct 102.00 line is dropped.
- `Total Item(s): 4` → matches TOTAL tier, number `4` found.

Because the agent's `extract_total` takes the LAST tier-4 candidate and `Total Item(s)` is the last `\bTOTAL\b` hit, you'd expect `4.00`. The actual delivered value `702.00` means either:
- `Total Item(s)` line was mangled further by OCR so it failed the `\bTOTAL\b` boundary, leaving `Total inel. of GBT 702.00` as the last tier-4 match, or
- A later edit added "Item(s)"/single-digit exclusions that filtered `Total Item(s)` out, again leaving the OCR-corrupted 702.00 line as the winner.

Either way the root causes are:
1. OCR corruption `1→7` in `102.00` and `Total→Tolal/Toial` were not mitigated by multi-pass OCR, image preprocessing, or vision OCR.
2. No numeric sanity: the extractor never cross-validates the chosen total against `Subtotal 102.00`, `Payment 102.00`, `Change 0.00`, or the GST summary `96.23 + 5.77 ≈ 102.00`. Any of these would have ruled out `702.00`.
3. No OCR character-substitution recovery inside amount tokens (e.g., leading `7` where 2 other instances of the same amount read `1`).
