### single-pass-ocr-default | operation | executor runs only `pytesseract.image_to_string(img)` with no preprocessing/PSM variants, so single-glyph OCR errors (3→8 on 034 month, 1→7 on 074 amount, decimal→space/colon on 078) silently propagate into the output

- anchor: multi-pass-ocr-strategy
- appeared_in: iter_0
- description: The source agent used a single Tesseract pass with default PSM 3 on the raw PIL image for every receipt. `n_skill_invocations=0` — the `image-ocr` Skill's documented `multi_pass_ocr` recipe (preprocess variants × PSM 6/4/11, aggregate) was NEVER invoked. Image-grounded evidence from w0001, w0010, w0019, w0034, w0035, w0037: every one of the four shipped errors reduces to a single-glyph or single-line OCR corruption that a second preprocessing pass (grayscale + autocontrast + PSM 6, or a 2×/3× upscale + PSM 4) demonstrably recovers in isolation (034 → `09/03/2018`; 074 → `102.00`; 078 → `Grand Total a 92.80`). The agent repeatedly discovered this mid-run (w0004, w0012, w0017, w0030, w0037) but the fix landed as a code edit immediately before `max_iterations` termination without an end-to-end re-run, so the shipped xlsx still reflects single-pass behaviour. The current SKILL.md body already contains a `multi_pass_ocr` function pointer but does not mandate its use for receipt-grade extraction and does not tell the executor how to *combine* text across passes — merely `"\n".join(all_text)`, which is insufficient when passes disagree on digits.
- latest_executor_action: For any receipt / low-contrast scanned-document OCR task, do NOT ship a pipeline that calls `pytesseract.image_to_string(img)` only once with default PSM. Always run ≥3 variants — baseline (default PSM), preprocessed (grayscale + autocontrast + PSM 6), and upscaled (≥2× LANCZOS + autocontrast + PSM 6 or PSM 4) — and keep per-variant line-level text so downstream extractors can vote. Do this up front, before writing any extractor, so that the output xlsx reflects multi-pass results even if the iteration budget runs out while tuning per-field rules.

### amount-candidate-selection-within-total-tier | operation | when multiple TOTAL-family lines exist on one receipt, executor's within-tier tie-breaker picks the wrong line (last-decimal-wins hits OCR-corrupted `702.00`; first-match hits pre-rounding `23.26` instead of post-rounding `23.25`)

- anchor: receipt-total-selection
- appeared_in: iter_0
- description: Across 12+ windows (w0003, w0004, w0005, w0006, w0007, w0011, w0013, w0014, w0018, w0021, w0027, w0036) the agent oscillated between "first candidate in TOTAL tier wins" and "last candidate in TOTAL tier wins" (via `reversed(matches)`). Neither rule handles both 074 and 077 correctly: 074 needs the EARLIER tier-match preferred (because the last-matching `Total Amt Rounded` line is OCR-corrupted to `702.00` while 102.00 appears on Subtotal/Total Incl./Payment ≥3× — within-text frequency consensus wins); 077 needs the LAST matching bare `TOTAL:` preferred (because `Total (Inclusive of GST): 23.26` comes before the post-rounding bold `TOTAL: 23.25`). The root unifier is: within the same keyword priority tier, prefer the value that (a) appears most often across *all* total-adjacent lines in the same OCR text (fixes 074: 102.00 appears 3–5×, 702.00 once), AND (b) when multiple distinct values tie on specificity, prefer the one on a bare `^TOTAL\s*:` line following a `Rounding Adj` / `ROUNDED` marker over one qualified by `(Inclusive of GST)` / `(Excluding GST)` / `Incl.` / `Excl.` (fixes 077). Cross-variant majority voting without within-text frequency fails on 074 because 2 of 3 OCR variants independently misread `1→7` on the same glyph, so variant-majority entrenches the wrong digit (w0006, w0015, w0036).
- latest_executor_action: Within a priority tier for receipt amount extraction, score each (line, value) candidate by: (1) specificity of the keyword (bare `TOTAL:` or `TOTAL RM` or `GRAND TOTAL` outranks `Total (Inclusive of GST)` / `Total (Excluding GST)` / `Total Amt Rounded` / `Total Items`); (2) within-text corroboration — how many OTHER lines on the same receipt (Subtotal, Payment, Rounded Total, Change-plus-math) produce the same numeric value; (3) position relative to `Rounding Adj` / `ROUNDED` markers — prefer the TOTAL line AFTER such a marker. Only use cross-variant voting as a final tiebreaker, never as the primary selector, because 2-of-3 variant agreement on a single-glyph misread (074's 702.00 case) will defeat a single correct variant.

### exclusion-and-fallback-keyword-gaps | operation | hint-level exclusion list (`SUBTOTAL`, `CASH TENDERED`, `CHANGE`, tax/GST/SST, `DISCOUNT`) misses real-receipt payment/column-header lines (`CASH RECEIVED`, `PAYMENT`, `VISA`, `MASTERCARD`, `DESCRIPTION`, `QTY PRICE AMOUNT`, `AVERAGE/PAX`) so the split-line fallback drops into item rows or payment rows and returns wrong values or null

- anchor: receipt-exclusion-and-fallback
- appeared_in: iter_0
- description: Three distinct fallback leaks are visible: (a) 064 variant OCR `Total RM = B81?` had no decimal on the keyword line, so the "next line last number" fallback grabbed `Visa RM =688.17` (`VISA` not excluded) — fixed mid-run via "fallback only if keyword line has NO digits" (w0025 m0147), but the symmetric payment-row problem persists elsewhere; (b) 078 upscaled OCR produced `Grand Total` with no number parseable (either `92:80` colon-decimal or decimal eaten), fallback walked past and hit `Cash Received 100.00` (not in exclusions) or an item row (`4132 CROCS ... 20.00`) because the column header `Description Qty Price Amount` matched the tier-3 `AMOUNT` keyword; (c) 077's `Total (Excluding GST)` is correctly suppressed by adding `EXCLUDING` to exclusions, but this alone does not resolve the inclusive-vs-rounded ambiguity. The task-hint's exclusion list is incomplete for real-world receipts; the Skill does not document this gap. Related: the `extract_last_number` regex requiring strict `\d+\.\d{2}` rejects OCR variants that drop a decimal (`92.80` → `92 80` or `92:80`), suppressing legitimate candidates on precisely the lines that most need rescuing (078 Grand Total line).
- latest_executor_action: For receipt amount extraction, extend the hint-level exclusion list to cover payment-instrument and received-cash lines: `CASH\s+(RECEIVED|TENDERED|PAID|PAYMENT)`, `\bPAYMENT\b`, `\bVISA\b`, `\bMASTERCARD\b`, `\bCARD\b`, `\bTENDER`, and column-header shapes `\bDESCRIPTION\b`, `\b(QTY|PRICE)\s+AMOUNT\b`, `\bAVERAGE\b.*\bPAX\b`. Gate the "next-line last-number" fallback on "keyword line has no digits at all" (so only genuinely-split layouts trigger it). When an amount line matches a priority keyword but the extracted token is garbled (`92:80`, `92 80`, trailing non-numeric glyphs), normalize `:` and single-space between digits to `.` BEFORE applying the 2-decimal regex, but only within that keyword line (not globally — avoids corrupting time stamps).

### date-anchoring-and-dmy-locale | operation | date extractor scans globally with no label anchor, so time-adjacent tokens (`08:49:00`), handwritten annotations (`A03041`, `GA1801`), or OCR 3→8 digit confusions bleed into the final date; DD/MM/YYYY vs MM/DD/YYYY is not locked to the Malaysian corpus

- anchor: receipt-date-extraction
- appeared_in: iter_0
- description: 21/22 dates parse correctly on the dataset, so the general DD/MM/YYYY regex and ISO normalizer are sound. The sole failure, 034.jpg, has pixel date `Date: 09/03/2018` with time `08:49:00` on the next line and handwritten `A03041` nearby. The predicted `2018-08-09` is consistent with (i) OCR misreading `03`→`08` on a thin-stroke digit, or (ii) the date regex latching onto the `08` of the time field, or (iii) a late MM/DD fallback firing when day≤12 so no DD/MM lock-in signal exists on this receipt. Fix is fan-out: (a) anchor date candidates to the same OCR line as a literal `Date` / `Tarikh` / `Invoice Date` label and reject matches whose "month" came from a `HH:MM` slot; (b) when the entire receipt corpus is known to be Malaysian, default to DD/MM/YYYY first and only fall back to MM/DD when the first group >12; (c) cross-OCR-variant voting on the date when multiple preprocessing passes are run (not a rescue when all variants share the same `3↔8` confusion, but cheap).
- latest_executor_action: When extracting dates from Malaysian/APAC receipts: (1) parse per OCR variant separately and keep the labeled match (same line as `Date`/`Tarikh`/`Dated`) with highest priority — do NOT compose day/month/year tokens from different lines; (2) default to DD/MM/YYYY; (3) reject any date candidate whose month field appears to come from a `HH:MM(:SS)` time pattern on the same line; (4) when ≥2 OCR variants are available, vote across variants but require the voted date to be a valid calendar date (month 1..12, day 1..31, year in reasonable receipt-era range 2010..current).
- remedy_log:
  - iter_0 | diagnosis: 034's predicted `2018-08-09` came from either time-digit bleed (`08:49:00`) or 3→8 OCR misread; date regex is global and label-agnostic; 21/22 correct suggests DD/MM/YYYY parse itself is fine, only candidate selection breaks on this edge case

- appeared_in: iter_0
- description: Every window ends with `termination_reason: max_iterations`, `acp_stop_reason: max_turn_requests`, `n_skill_invocations=0`. Over 27 terminal + 22 think + 16 file_editor calls the agent iteratively (a) inspected OCR for individual receipts, (b) edited `extract.py`, (c) oscillated between "first-wins" and "last-wins" within-tier selection and between "default-first" and "preprocessed-first" OCR variant ordering, each time fixing one receipt and regressing another (074 ↔ 077 ↔ 078 ↔ 034 ↔ 064 ↔ 052 ↔ 071). Secondary cause: the agent hand-rolled OCR instead of invoking the `image-ocr` Skill's multi_pass recipe.
- latest_executor_action: For batched image-OCR extraction tasks: (1) first iteration must produce a cached per-image OCR text store containing ALL variants (default, preprocessed, upscaled) — this freezes OCR cost and makes subsequent extractor edits in-memory; (2) extractor heuristics iterate against the cache, not against re-OCR'd pixels, freeing budget for logic refinement; (3) write the xlsx deliverable as the last step of EVERY extractor edit (idempotent re-run), so budget exhaustion still ships the best-known-good artifact; (4) explicitly invoke the `image-ocr` Skill's `multi_pass_ocr` recipe (or equivalent inline code) rather than re-implementing single-pass OCR; (5) before the first write, run the pipeline end-to-end on all images once, so termination at any later iteration still delivers a complete artifact.
