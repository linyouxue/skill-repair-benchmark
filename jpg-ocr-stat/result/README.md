# 上传最终修复好的Skill

每个“方法＋配置”在本目录提交一个最终冻结版本，顶层仍只有 **`skills/`、一份简短的`README.md`、`evidence/`**。**最终Skill须在原22张小票任务上独立运行3次，分别报告字段正确率，再取三次的算术均值。** 每份最终Skill必须附上真实修复过程，以及三次执行各自的完整轨迹、实际生成的原Excel和评分记录。后续扩展小票的泛化评测另行组织，不是本次上传要求。

```text
result/
├── README.md                         # 本上传说明，保留不覆盖
└── <method_id>__<config_id>/          # 替换为自己的方法和配置标识
    ├── skills/                      # 最终完整5个Skill及支持文件、许可
    ├── README.md                    # 简短说明：方法、配置、版本及必要披露
    └── evidence/                    # 修复过程、最终执行轨迹、原Excel及评分证据
```

上面是目录格式示例，不代表已有方法提交。目录标识建议使用英文字母、数字、连字符或下划线；不同配置分别建目录。同一方法配置只提交一个最终版本，不根据后续泛化成绩回头挑选候选。

## 三项分别放什么

| 内容 | 上传要求 |
| --- | --- |
| `skills/` | 直接包含`image-ocr/`、`openai-vision/`、`pdf/`、`video-frame-extraction/`、`xlsx/`五个目录。提交完整最终文件，不只交diff；只允许修改这五份现有`SKILL.md`，其余支持文件和许可保留原样。 |
| `README.md` | 几行说明方法、修复模型与最终执行模型配置、代码与最终Skill版本，以及材料使用、人工参与和样本专用内容。列出三次原任务字段正确率及均值，标明各次run ID、原Excel和证据位置。已有配置或日志可直接引用，不必重抄。 |
| `evidence/` | 同时保存两类证据：方法诊断/修改/选版的真实修复过程，以及同一最终冻结Skill在原22票任务上的三次独立完整执行、各次真实原Excel和评分记录。两类轨迹不能互相替代；方法内部已有执行只有确实使用同一最终版本且符合下述65轮规范时，才可计入三次最终执行证据。 |

不强制手工另写`submission.json`、`diagnosis.md`、`history.md`或`coverage.json`。已有文件可以原样放入证据，不用重新整理原始日志；只需在README汇总三次成绩和均值。执行器实际生成的`result.json`等运行元数据应原样保留，不能用过程归档工具的同名收据替代。

## 原22张任务：独立运行3次，取均值

三次均使用同一个最终冻结Skill、相同执行模型和配置，分别从原任务的初始状态开始，每次最多65次父迭代。不要把一次运行的断点接续或三次免费评分当作三次独立执行，也不要把不同Skill版本的成绩混算。

每次用本任务的[字段正确率verifier](../README.md#评分口径)评分，固定44字段；最终均值为`(第1次字段正确率 + 第2次字段正确率 + 第3次字段正确率) / 3`。保留三次全部结果，不只报最高分。普通FAIL、错误预测和空字段照实计分；基础设施故障单列说明，未完成三次时不要把一两次结果标成“三次均值”。

已有符合相同冻结版本和执行规范的真实运行可计入三次，只补足缺少的次数；每次仍须有独立run ID及对应原Excel、完整轨迹和评分记录。

## 真实Excel与两类轨迹怎样放

参考本仓库[evaluation/results的提交说明](https://github.com/linyouxue/skill-repair-benchmark/blob/main/evaluation/results/README.md)。该实例将`repair_generation/`与`repaired_run/`分开：前者是修改Skill的过程，后者是使用修复Skill完成任务的过程。

下列是放在自己提交目录内的示意。可以直接保留原方法/执行器导出的目录名，只要README指向清楚；不用转写真实日志或为示例制造文件。

```text
evidence/
├── repair/                          # 诊断/修改请求响应、图片传入及迭代选版证据
└── final_runs/                      # 顶层skills/同一冻结版本，原22票独立3次
    ├── run_01/
    │   ├── executor_request.json    # 真实任务、模型与执行配置
    │   ├── result.json              # 原始执行元数据、上限、实际迭代与终止原因
    │   ├── benchmark_result.json    # 执行器生成的结果记录（存在时原样保留）
    │   ├── trajectory/              # 完整ACP及完整LLM请求响应，允许无损压缩
    │   ├── artifacts/               # 必须包含该次执行的原stat_ocr.xlsx
    │   └── verifier/                # 实际字段评分、CTRF及reward等原始记录
    ├── run_02/...                   # 同样保留第2次的原Excel、轨迹及评分
    └── run_03/...                   # 同样保留第3次的原Excel、轨迹及评分
```

- `trajectory/`保留`acp_trajectory.jsonl`及`llm_trajectory.jsonl`（或其无损压缩版）；方法的诊断模型日志另外放在`repair/`。同时保留已有配置、时间、用量和其它执行器原生文件，不只交一份汇总成绩。
- `artifacts/stat_ocr.xlsx`必须来自这次最终Skill执行。若只存在于原生`pre-verifier-inputs.tar.gz`等归档，解出原Excel并按字节核对；原归档也保留。不要从预测JSON、模型文字或baseline Excel重新造表，也不要人工补齐预测。
- 原Excel按原22票、44字段评测，表结构沿用[任务说明](../README.md)；错误预测、缺行或null如实保留，不人工补齐，缺失字段仍计入固定分母。不要求全对才上传；普通FAIL或达到迭代上限也保留真实Excel及原终止状态，不改写为自然完成。
- 未生成Excel、缺少执行轨迹或尚未执行的版本可保留失败/待完成记录，但不算完成了最终交付。不能用旧版本的执行记录顶替，也不因此自动无限重跑。多次执行使用不同run ID并保留已有记录，指出最终版本对应哪些运行，不只挑最好的一次。

## 最终任务执行上限：65次父迭代

本次JPG最终执行规范为：**原22票任务的每次根Agent执行最多65次parent iteration**，可提前自然结束；这与给定Opus原始Skill轨迹的65轮上限一致。completion guard如启用，续行也使用同一65轮剩余额度。这里的计数是根会话的`agent.step()`，不是外部工具次数、token数，也不是包含网络重试的累计HTTP次数。

65限制的是使用冻结Skill执行任务的单次运行，不统一改动方法自己的诊断、修复、候选迭代或停止策略，也不是方法总token或费用上限。README和真实执行记录应能核对配置上限、实际迭代数及终止原因；例如已有执行器的`executor.max_parent_iterations_per_step`、`prompt_runs[].max_iterations/iterations_used/stop_reason`及ACP迭代结束事件。实际不到65次不代表上限配置错误，需同时看配置与终止原因。

**接入状态：这是本任务的65轮提交规范，不表示当前全仓库执行器已自动切换。** 当前公开BenchmarkExecutor仍固定60，且会覆盖调用方的`BENCHMARK_EXECUTOR_MAX_ITERATIONS`；单独设置环境变量为65不会生效。接入端需要把JPG选定的65轮贯通执行配置、实际OpenHands会话、运行元数据与一致性检查，核验实际生效后再按此规范提交。不要只把README或旧运行记录中的60改成65。本PR不修改全局默认值或已有实验，旧SROIE的60轮baseline保留原协议，不能当作65轮结果混报。

## 修复与证据边界

- 修复使用本任务原22张票、原Task、原Skill和[给定诊断包](../diagnosis/README.md)及其中允许的反馈；不读取oracle解法、参考答案值或verifier断言。此前扩展数据集留给后续泛化评测，不用于本轮修复或选版。此前已接触或额外使用过材料的情况如实说明，不能据此声称严格未见。
- 保留方法自身的迭代、干预、候选选择和停止机制。方法需要时可以在原22张票上新增执行，并记录新增调用、轨迹、反馈和选版依据；这与上述最终冻结版本的65轮任务执行分开，不给方法诊断/修复过程新增统一token、迭代轮数或费用限制。
- 保留方法实际生成的最终Skill。样本专用规则或示例只要求披露位置与作用，不据此自动删除、改写或拒收。人工参与也要说明，不把人工再修改后的版本冒充方法原始输出。
- 证据中的请求记录应能看出实际发送了哪些文本和图片内容块，并对应到原图或真实裁剪图。只列文件路径、把Base64当普通文本，或提供数据集侧预制packet，都不能证明方法实际向模型传过图片；准备输入也不等于已发送。没有实际传图就如实记录。
- 不用重复上传已发布的原图或原轨迹，可引用其仓库版本与路径。新增图片须提供真实文件或归档对应关系。日志可以保留原格式并压缩；大日志可在`evidence/README.md`中给出可访问的归档链接、成员说明和对应关系。上传前移除凭据、认证头和无关个人信息，缺失的记录如实标注，不补造。已有用量记录可一并保留，不要求为上传另写成本报表。

## 怎样整理并上传

1. 从仓库当前main创建自己的分支或fork，在`jpg-ocr-stat/result/`下创建`<method_id>__<config_id>/`。保留本上传说明和其他方法的目录。
2. 将已冻结的最终Skill目录复制为其中的`skills/`，按模板写几行`README.md`及三次成绩与均值，将真实修复过程、同一最终版本的三次65轮规范任务执行记录、各次原Excel及评分证据放入`evidence/`。原方法的配置和日志无需改成统一schema；本说明不是已经执行任何新实验的记录。
3. 核对五个Skill及支持文件、许可完整，三次原Excel与各自运行一致，修复/执行两类轨迹齐全，65轮配置有实际证据，三次成绩及均值可核对，说明中的路径或归档链接可访问，文件不含凭据，再提交面向main的PR。PR中写清方法与配置标识、最终版本和本次上传目录即可。

如果已经使用[可选的`save-result`工具](../diagnosis/README.md)，先在任务包外、候选Skill目录外生成归档，再把其`skills/`用于最终提交，其余真实记录按需放入`evidence/`，并附上方法实际日志。不要直接用该工具写入本任务包内的`result/`。它的`model_calls_by_helper=0`只表示辅助工具没有调用模型，不代表修复方法没有调用模型。

泛化测试使用本目录已冻结的`skills/`，**当前只在group2（20张）运行3次，group1、group3暂时不用跑**。泛化结果按[独立上传说明](../evaluation/results/methods/README.md)提交到`jpg-ocr-stat/evaluation/results/methods/`；本目录保留Skill和修复证据，不重复上传。
