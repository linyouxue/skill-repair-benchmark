Container LANG/LC_ALL = C (platform encoding = ANSI_X3.4-1968 / ASCII)

===================================================================
Root cause: the container's default file.encoding is ASCII
===================================================================

The build runs on a container whose default locale is "C", so every JVM
started by Maven inherits `file.encoding=ANSI_X3.4-1968` (US-ASCII). The
Auto project uses UTF-8 source files that contain non-ASCII characters
(e.g. "é" in author tags and "©" in some comments), and three places in
the build do NOT force UTF-8 on the compiler/JVM:

  1. The maven-surefire-plugin forks a test JVM to run unit tests of the
     `value` module. That JVM runs
     `com.google.auto.value.processor.AutoAnnotationCompilationTest`.
     `testMissingClass` creates a fresh `JavaCompiler` task via
     `ToolProvider.getSystemJavaCompiler()` with no `-encoding` option,
     so the javac in the forked VM uses platform encoding (ASCII) when
     reading sources passed to the task. The compiler reports:
       "unmappable character for encoding ASCII"
     and the test's assertion
       assertThat(diagnostics.get(0).getMessage(null)).contains("NotAutoAnnotation")
     fails because the first diagnostic is the encoding error, not the
     expected "NotAutoAnnotation" error.
     => Result: 1 failing test, surefire fails the `value` module's
        test phase.
     => Confirmed fix: forking the test JVM with
        `-Dfile.encoding=UTF-8` makes testMissingClass pass and leaves
        all 172 unit tests green.

  2. The maven-invoker-plugin runs `src/it/functional` as a nested
     Maven build. `value/src/it/functional/pom.xml` has NO parent and
     does NOT declare `project.build.sourceEncoding`, so the nested
     maven-compiler-plugin uses the platform encoding (ASCII) to read
     the Java test sources, several of which contain non-ASCII
     characters (e.g. "é" in `@author` tags in AutoValueTest.java,
     SimpleValueTypeTest.java, MyEnum.java, PackagelessValueTypeTest.java,
     PackagelessValueType.java, PackagelessNestedValueType.java).
     The nested build fails with multiple
       "unmappable character for encoding ASCII"
     errors in src/test/java.
     => Result: invoker-plugin reports `functional/pom.xml` FAILED and
        the `value` module `verify` phase fails.
     => Fix 2a: add `<project.build.sourceEncoding>UTF-8</...>` to
        `value/src/it/functional/pom.xml`.

     SECOND, independent issue in the SAME nested build: AutoValueTest.java
     imports `com.google.common.base.MoreObjects` (added in guava 18.0,
     courtesy of commit 317dcc8 "Migrate users from c.g.c.base.Objects
     to MoreObjects.") but the dependency tree for functional/pom.xml
     resolves guava to 17.0:
       functional
         +- com.google.truth:truth:0.25   -> com.google.guava:guava:17.0  (test)
         \- com.google.guava:guava-testlib:18.0 -> com.google.guava:guava:18.0 (test)
     Both candidates are at the same depth and Maven's declaration-order
     tiebreaker picks the one that was declared first, so guava 17.0
     wins. 17.0 does NOT contain MoreObjects, so test compilation fails
     with
       cannot find symbol: class MoreObjects
       location: package com.google.common.base
     (A later upstream commit, aa77281 in Jan 2016, fixed this exact
     issue by adding an explicit guava direct dep.)
     => Fix 2b: pin guava to 18.0 by adding an explicit
        <dependency>com.google.guava:guava:18.0 (test)</dependency>
        to `value/src/it/functional/pom.xml`.

  3. The maven-invoker-plugin also runs `src/it/gwtserializer`.
     Its pom likewise has no `project.build.sourceEncoding`, giving the
     warning
       "File encoding has not been set, using platform encoding
        ANSI_X3.4-1968, i.e. build is platform dependent!"
     This nested build currently passes because its source files are
     pure ASCII, but it is latent breakage; set the encoding there too
     for consistency and future-proofing.

Nothing is wrong with the production code. All changes are build /
configuration only.

===================================================================
Plan (changes to apply)
===================================================================

Patch 1 -- value/pom.xml
  Add a maven-surefire-plugin configuration with
    <argLine>-Dfile.encoding=UTF-8</argLine>
  inside the existing <build><plugins> section of the value module.
  Fixes the AutoAnnotationCompilationTest.testMissingClass failure
  (root problem reported by the failed Travis build).

Patch 2 -- value/src/it/functional/pom.xml
  Add
    <properties>
      <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
  before <dependencies>. Fixes the nested compilation failure of the
  functional IT caused by non-ASCII characters in the test sources.

Patch 3 -- value/src/it/gwtserializer/pom.xml
  Add the same <properties>/<project.build.sourceEncoding> block.
  Removes the "platform encoding ANSI_X3.4-1968" warning and makes the
  IT build encoding-independent.

Patch 4 -- value/src/it/functional/pom.xml
  Add an explicit
    <dependency>com.google.guava:guava:18.0 (test)</dependency>
  entry so that the direct dependency wins over the guava-17.0 pulled
  in transitively by truth 0.25, which exposes MoreObjects (added in
  guava 18.0) needed by AutoValueTest.java.
