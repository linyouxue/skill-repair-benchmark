===========================================================
FAILING STEP INSIDE THE INTEGRATION TEST
===========================================================
File: value/target/it/functional/build.log

mvn goal:
  org.apache.maven.plugins:maven-compiler-plugin:3.1:testCompile
   (default-testCompile) on project functional

Errors reported:

  1) "unmappable character for encoding ASCII"
     Several test and main source files contain non-ASCII (UTF-8)
     characters (e.g. "Éamonn" in AutoValueTest.java line 50),
     but the Maven compiler plugin falls back to the platform
     default encoding (ANSI_X3.4-1968 / ASCII) because no
     project.build.sourceEncoding is defined for
     value/src/it/functional/pom.xml.  During src/main compile
     these appear as WARNINGS; during src/test compile they are
     reported as ERRORS and fail the build.

     Affected files:
       src/test/java/com/google/auto/value/AutoValueTest.java [50,33]-[50,34]
       src/test/java/com/google/auto/value/SimpleValueTypeTest.java [26,*]
       src/test/java/com/google/auto/value/enums/MyEnum.java [19,*]
       src/test/java/PackagelessValueTypeTest.java [25,*]

  2) "cannot find symbol class MoreObjects"
     AutoValueTest.java (line 20, 72) imports and uses
     com.google.common.base.MoreObjects, which only exists in
     Guava 18.0 or later.

     Why Guava 17.0 is on the classpath:
       value/src/it/functional/pom.xml declares, in this order:
         - auto-value          (dependency-reduced-pom has no guava dep,
                                because the shade plugin relocated it)
         - jsr305
         - junit
         - truth 0.25          --> transitively depends on guava 17.0
         - guava-testlib 18.0  --> transitively depends on guava 18.0
       Both guava versions appear at depth 2 in the dependency tree,
       so Maven's "nearest definition / first-declared wins" rule
       picks the earlier one: guava 17.0 from truth 0.25.

       There is no direct <dependency> on com.google.guava:guava,
       so the test code compiles against 17.0 and cannot find
       the MoreObjects class that was added in 18.0.

===========================================================
WHY THE BugSwarm PATCH ALONE DID NOT CAUSE THIS
===========================================================
HEAD (commit 484f5ae) is a BugSwarm patch that:
  - Only reformats pom.xml whitespace / encoding tag spelling
    (semantically identical).
  - Appends "-Dhttps.protocols=TLSv1.2" to
    value/src/it/functional/invoker.properties and
    value/src/it/gwtserializer/invoker.properties.
None of these changes alter the dependency tree or the compiler
encoding; the two build errors above pre-exist in the HEAD state
being reproduced by BugSwarm.  They are what makes the build fail
today, so they are what we must fix.

===========================================================
FIX PLAN (minimal and local to the failing module)
===========================================================
Only one file needs to change: value/src/it/functional/pom.xml

  (a) Add a <properties> block with
          <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
      so the maven-compiler-plugin compiles sources as UTF-8 instead
      of ASCII. This fixes the "unmappable character" errors for all
      the affected test and main source files.

  (b) Add a direct dependency on com.google.guava:guava:18.0 (test
      scope) BEFORE the truth dependency, or just rely on the fact
      that a direct dependency always wins over any transitive one.
      This pins Guava to 18.0 so that com.google.common.base.MoreObjects
      is available during test compilation and execution.

No source code is modified. No other POM is modified. The
gwtserializer integration test and the other modules already pass
and are left untouched.
