Failing test
------------
Module : value (AutoValue)
Suite  : com.google.auto.value.processor.AutoAnnotationCompilationTest
Test   : testMissingClass
Error  :
    java.lang.AssertionError:
        Not true that <"unmappable character for encoding ASCII">
                 contains <"NotAutoAnnotation">
    at AutoAnnotationCompilationTest.doTestMissingClass:401

Root cause
----------
The test invokes `javaCompiler.getTask(...)` in-process (via tools.jar) with
a default JavaFileManager and no `-encoding` option. The processor under test
(AutoAnnotationProcessor) is a `javax.annotation.processing.Processor` whose
`.class` is read by javac via the stub-reading path. The default charset of
the running JVM is used; when the Surefire-forked JVM inherits a C/POSIX
locale, `file.encoding` becomes US-ASCII.

Several source files in value/ contain the character "É" (as in
"Éamonn McManus" in @author tags).  These were compiled OK by maven-compiler
because the parent pom sets `project.build.sourceEncoding=UTF-8`, so the plugin
passes `-encoding UTF-8` to javac.  But at test-time the forked JVM runs with
`file.encoding=US-ASCII`.  When the test's embedded javac performs its parsing
pass to decide on processors and read associated files/stubs, it emits the
diagnostic "unmappable character for encoding ASCII" BEFORE emitting the real
diagnostic about the undefined symbol `NotAutoAnnotation`.  The test picks
`diagnostics.get(0)` and asserts it contains "NotAutoAnnotation" -> AssertionError.

Verification
------------
Running the same build with the locale forced to UTF-8:
    LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 mvn -f build-pom.xml -pl value test \
        -Dtest=AutoAnnotationCompilationTest
produces: Tests run: 4, Failures: 0, Errors: 0, Skipped: 0  (BUILD SUCCESS).

This confirms the failure is purely an encoding-of-the-test-JVM problem; the
code is correct, the build configuration is at fault.

Note on the BugSwarm HEAD commit
--------------------------------
The HEAD "BugSwarm patches" commit reformatted pom.xml extensively (one XML
element per line) and added `-Dhttps.protocols=TLSv1.2` to a couple of
invoker.properties files.  The reformatting also DROPPED the final newline on
pom.xml ("No newline at end of file") but kept all the semantics.  Those
changes are not the direct source of this test failure; the failure comes
from the test JVM's default charset.

Fix plan
--------
Add a maven-surefire-plugin configuration in the top-level parent pom.xml
that forces the test JVM to use UTF-8:

    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
      <configuration>
        <argLine>-Dfile.encoding=UTF-8</argLine>
      </configuration>
    </plugin>

Placement: inside the existing <build><plugins>...</plugins></build> block
of /home/travis/build/failed/google/auto/pom.xml (next to maven-compiler-plugin
and maven-checkstyle-plugin).  No plugin version is needed - Maven resolves
the default version for surefire.

This is a minimal, locale-robust fix that matches the project's declared
source encoding (UTF-8).  It fixes testMissingClass regardless of the host's
LANG, without touching any Java source or test.

Invoker integration test "functional" surfaced:

(2) The IT project value/src/it/functional/pom.xml does NOT inherit from

(3) The IT project declares test deps truth:0.25 and guava-testlib:18.0.

    (added in 18.0), so AutoValueTest.java fails to find the class.
    -> patch_3.diff: add explicit `com.google.guava:guava:18.0` test dep in
       functional/pom.xml so guava 18 wins resolution.
