Repository: /home/travis/build/failed/google/auto
Build command (from .travis.yml):
    mvn -B -U -f build-pom.xml verify --fail-at-end -Dsource.skip=true -Dmaven.javadoc.skip=true

Result (before fixes): BUILD FAILURE in module `auto-value` (value/pom.xml) at test

Result (after fixes):  BUILD SUCCESS, all 6 reactor modules.


ROOT CAUSE
----------

The build has three independent problems that all surface because the container
in which Travis is reproduced here runs with LANG=C / LC_ALL=C, which makes the
JVM's default `file.encoding` be `ANSI_X3.4-1968` (ASCII).

Several source trees in this project contain non-ASCII characters, most notably
"Éamonn McManus" in JavaDoc comments. When javac is invoked without an explicit
encoding, those files emit "unmappable character for encoding ASCII" and
compilation fails.

Problem 1 - Surfacing diagnostic (the originally reported failure)
    com.google.auto.value.processor.AutoAnnotationCompilationTest.testMissingClass
    expects the first compiler diagnostic to contain "NotAutoAnnotation".
    Because the test's inner javac invocation (ToolProvider.getSystemJavaCompiler)
    inherits `file.encoding=ASCII` from the Surefire JVM, the first diagnostic
    is "unmappable character for encoding ASCII" and the assertion fails.

Problem 2 - Integration test compilation (uncovered once problem 1 is fixed)
    `maven-invoker-plugin:run` builds value/src/it/functional and
    value/src/it/gwtserializer in nested Maven processes. Those invoked POMs
    do not set `project.build.sourceEncoding`, so maven-compiler-plugin logs
    "File encoding has not been set, using platform encoding ANSI_X3.4-1968"
    and compilation of the test sources fails with the same unmappable-character
    error.

Problem 3 - Latent dependency conflict (uncovered once problem 2 is fixed)
    `value/src/it/functional/pom.xml` declares `truth:0.25` before
    `guava-testlib:18.0`. `truth:0.25` depends transitively on `guava:17.0`;
    `guava-testlib:18.0` depends transitively on `guava:18.0`. With Maven 3.6.3
    the first-declared-wins rule resolves `guava:17.0`, which lacks
    `com.google.common.base.MoreObjects`. The test source
    `AutoValueTest.java` imports `MoreObjects` (added in a 2015 commit, see
    `git log -S MoreObjects`), so compilation fails with "cannot find symbol:
    class MoreObjects". The gwtserializer integration test is unaffected
    because it already declares `guava:18.0` explicitly.


FIXES APPLIED
-------------

patch_1.diff - value/pom.xml
    Add a maven-surefire-plugin configuration with
        <argLine>-Dfile.encoding=UTF-8</argLine>
    so the forked test JVM, and the javac it runs internally, use UTF-8
    regardless of the container locale.

patch_2.diff - value/src/it/functional/pom.xml and
               value/src/it/gwtserializer/pom.xml
    Add
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    to both nested integration-test POMs so maven-compiler-plugin reads the
    sources as UTF-8.

patch_3.diff - value/src/it/functional/pom.xml
    Add an explicit test-scope dependency on `com.google.guava:guava:18.0`
    (right after `truth:0.25` and before `guava-testlib:18.0`) so that
    `MoreObjects` is on the test classpath regardless of transitive-resolution
    order, matching what value/src/it/gwtserializer/pom.xml already does.
