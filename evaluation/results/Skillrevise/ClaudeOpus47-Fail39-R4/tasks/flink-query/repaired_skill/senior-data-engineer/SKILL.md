# Flink Event-Time Session-Stage Job Implementation

## Purpose
Reusable procedure for implementing or modifying an Apache Flink DataStream (Java/Scala/PyFlink) job that consumes a cluster/event trace CSV, groups events per key via an event-time inactivity gap, counts stages per key, and emits one record per key once the key terminates. Optimized for tasks where correctness depends on precise schema semantics (event-type codes, terminal states, timestamp units) and a specific output format enforced by a hidden verifier.

## When to Use
Trigger: the workspace contains a Flink job skeleton (pom.xml or build.sbt plus a partially written Java/Scala/Python source file) and the task asks you to implement session-based stage detection or similar event-time keyed aggregation over a schema-described CSV (e.g. Google cluster trace, resource manager logs). Use this skill whenever the correctness criteria depend on (a) numeric event codes defined in a companion schema document, (b) an inactivity gap definition, and (c) a strict output tuple format.

## Procedure
- Discover the environment. Run `ls`, `find . -maxdepth 4 -type f \( -name "pom.xml" -o -name "build.sbt" -o -name "*.java" -o -name "*.scala" -o -name "*.py" -o -name "README*" -o -name "*.md" -o -name "*.pdf" \)`. Identify: the Flink skeleton source file(s), the build tool, the input data path(s), the expected output path (from skeleton code, README, or run script), and all schema documentation files. Do not invoke helper scripts that are not present; do not assume the existence of generators or orchestrators.
- Verify the data schema before writing logic. Open every schema document (README, `.md`, `.pdf`). If a PDF is present, try extractors in this order until one yields readable text: `pdftotext file.pdf -`, `pdftotext -layout file.pdf -`, `python -m pdfminer.high_level file.pdf`, `pdf2txt.py file.pdf`, `strings file.pdf | less`. If all fail, search sibling files (`*.md`, `*.txt`) for the same schema. Record in a short notes block: (a) exact integer code for the SUBMIT / start event, (b) exact integer codes for every terminal state and whether the task specifies only successful completion or any terminal state, (c) timestamp unit (microseconds vs milliseconds vs seconds), (d) column order of the CSV, (e) whether the inactivity gap is strict `>` or inclusive `>=`, (f) how resubmissions should be counted (every SUBMIT, or only distinct task instances). If any item cannot be grounded in a schema source, mark it explicitly as an assumption and prefer the interpretation that matches the task instruction's literal wording.
- Restate the verifier contract. From the task instruction and any sample output, write down: output file path, record format (e.g. `(int,int)` one per line), key field, value field, sort order (if any), terminator newline. Do not finalize code until this contract is written.
- Implement the job logic against the recorded schema. Standard structure:
- Source: read CSV (handle gzip if files end in `.gz`), map to a typed POJO using the column order from step 2.
- Filter and route: keep only events relevant to the stage definition; convert the raw timestamp to a Flink event-time timestamp in milliseconds (apply the unit conversion identified in step 2).
- Assign watermarks with a bounded out-of-orderness tolerance; key the stream by the key field (e.g. job_id).
- Use a `KeyedProcessFunction` (or session window) that: increments a stage counter on each SUBMIT event when the gap since the previous SUBMIT for that key exceeds 10 minutes (apply the inequality chosen in step 2); registers an event-time timer at `last_submit_ts + 10min`; on key termination (terminal event per step 2) emits `(key, stage_count)` and clears state. Count every SUBMIT as per step 2's resubmission rule.
- Build. Use the project's declared build tool: `mvn -q -DskipTests package` or `sbt package`. Fix compilation errors locally; do not reshape the project layout.
- Smoke-run and verify output format. Execute the job against the provided sample input using the entrypoint declared in the skeleton or README. Then: confirm the output file exists at the exact path from step 3; `head -n 20` and `tail -n 20` the file; assert every line matches the required format with a quick check (e.g. `awk -F'[(,)]' 'NF!=4 || $2!~/^-?[0-9]+$/ || $3!~/^-?[0-9]+$/ {print "BAD:",NR,$0; exit 1}' output_file`); confirm counts are non-zero where expected. If any check fails, return to step 2 or 4; do not declare completion.
- Finalize. Leave the schema notes from step 2 and the contract from step 3 as comments at the top of the modified source file so the decisions are auditable.

## Constraints / Pitfalls
- Do not invent or invoke helper scripts (DAG generators, config generators, orchestrators) that are not present in the workspace. Edit the actual Flink source file in place.
- Never guess event-type integer codes, terminal-state codes, or timestamp units. If schema extraction tools all fail, document the fallback assumption explicitly and prefer the interpretation most literal to the task statement.
- Distinguish terminal states carefully: "job finished" in a task instruction may or may not include KILL/FAIL/EVICT. Encode the chosen set in one constant and justify it from the schema doc.
- Choose the gap inequality (`>` vs `>=`) deliberately. A 10-minute gap defined as "no SUBMIT for 10 minutes" is typically strict `>` on the elapsed delta; verify against any sample output if available.
- Count resubmissions per the task's literal wording. If the instruction says resubmits "should be counted separately," count every SUBMIT event, including repeats of the same task_index, as potential stage boundaries.
- Convert timestamps to milliseconds before assigning Flink event-time watermarks; Google cluster trace timestamps are microseconds and must be divided by 1000.
- Emit exactly once per key, on terminal event (or final watermark if the task allows), using the exact tuple format required by the verifier. No trailing commas, no extra whitespace, no header line unless specified.
- If a build or smoke-run step fails, inspect the failure signal and switch to the closest supported alternative (e.g. alternate PDF extractor, alternate run command from README) rather than silently skipping verification.
- Keep edits minimal and scoped to the skeleton; do not refactor package layout, rename classes, or add external dependencies beyond what pom.xml/build.sbt already declares.
