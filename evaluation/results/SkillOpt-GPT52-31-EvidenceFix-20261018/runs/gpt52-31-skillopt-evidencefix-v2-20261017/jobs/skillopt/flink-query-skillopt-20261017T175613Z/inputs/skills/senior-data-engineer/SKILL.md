# Senior Data Engineer

## Core Capabilities

- **Batch Pipeline Orchestration** - Design and implement production-ready ETL/ELT pipelines with Airflow, intelligent dependency resolution, retry logic, and comprehensive monitoring
- **Real-Time Streaming** - Build event-driven streaming pipelines with Kafka, Flink, Kinesis, and Spark Streaming with exactly-once semantics and sub-second latency


  - **Benchmark tip (Flink sessionization + gated emit):** For per-entity results that are only valid after completion (e.g., per jobId), enforce **inner-join semantics** by gating emission on a **schema-validated terminal event** and emitting **exactly once per key** using keyed state + event-time timers.
- **Data Quality Management** - Comprehensive batch and streaming data quality validation covering completeness, accuracy, consistency, timeliness, and validity
- **Streaming Quality Monitoring** - Track consumer lag, data freshness, schema drift, throughput, and dead letter queue rates for streaming pipelines
- **Performance Optimization** - Analyze and optimize pipeline performance with query optimization, Spark tuning, and cost analysis recommendations

## Best Practices



### Flink (Benchmark Pattern): Keyed Event-Time Sessionization + Gated Emit (task_events + job_events)

Use this pattern when you must compute a **per-job aggregate over task_events** but must **emit exactly one result only for jobs that truly terminate** in the provided **job_events** slice (inner-join semantics).

#### A. Schema-first filtering (do NOT infer terminals via broad predicates)
- **Validate event codes from the dataset docs** (e.g., Google cluster trace `format.pdf` / `ClusterData2011_2.md`).
- Filter task stream to **SUBMIT** only (and count resubmits as separate submits if required).
- Filter job stream to **qualifying terminal** events only (e.g., FINISH, KILL). Avoid heuristics like `eventType >= 3` unless the schema explicitly guarantees that meaning.

#### B. Stage/session definition (exact boundary semantics)
A “stage” is a run of SUBMIT events close in **event time** for a given `jobId`.
- Let `gap = 10 minutes` (in this benchmark timestamps are **microseconds**).
- Maintain `lastSubmitTs` per job.
- On a SUBMIT at time `ts`:
  - If `lastSubmitTs != null && ts - lastSubmitTs >= gap`, then **close the previous stage** and start a new one.
  - Important boundary: **`>= gap` starts a new stage**; `< gap` continues the current stage.
- Track:
  - `currentStageCount` (count of SUBMITs in current stage)
  - `maxStageCount` (largest stage seen so far)

#### C. Correlated dual-stream keyed processing (KeyedCoProcessFunction)
Key both streams by `jobId` and connect:
- `tasks.keyBy(jobId).connect(jobs.keyBy(jobId)).process(...)`

Recommended per-job state:
- `ValueState<Long> lastSubmitTs`
- `ValueState<Integer> currentStageCount`
- `ValueState<Integer> maxStageCount`
- `ValueState<Long> terminalTs` (earliest qualifying terminal)
- `ValueState<Boolean> seenSubmit`
- `ValueState<Boolean> emitted`

Processing logic:
- **On task SUBMIT (processElement1):** apply session boundary rules; update counts; set `seenSubmit=true`.
- **On terminal job event (processElement2):**
  - Store `terminalTs = min(existing, thisTerminalTs)` to handle duplicates.
  - Register an **event-time timer** at `terminalTs + allowedLateness` (or at `terminalTs` if lateness is 0).
- **OnTimer:** finalize and emit once:
  - `maxStageCount = max(maxStageCount, currentStageCount)`
  - Emit **only if** `emitted=false` AND `terminalTs != null` AND (optionally) `seenSubmit=true`.
  - Then set `emitted=true` and clear state.

Deterministic output semantics:
- **Exactly one output per jobId**, even if multiple terminal events exist.
- **Suppress output** for jobs that never show a qualifying terminal event within the input slice (common in partial datasets). Do **not** emit `(jobId,0)` defaults.

#### D. Event-time correctness: microseconds, watermarks, out-of-order, allowed lateness
- Treat timestamps as **microseconds** end-to-end; compute `gapMicros = 10 * 60 * 1_000_000L`.
- Prefer `WatermarkStrategy.forBoundedOutOfOrderness(...)` unless the data is guaranteed monotonic.
- Choose a small but explicit out-of-orderness bound for the benchmark (e.g., 1–5 minutes) and document it.
- Use `allowedLateness` by delaying the timer to `terminalTs + allowedLateness` to avoid premature emission when late SUBMITs arrive before the watermark passes.
- Late-event policy must be explicit:
  - ignore tasks with `ts > terminalTs` (if defined as after-job-finish), or
  - support corrections only if the sink supports upserts (not typical for this benchmark).

#### E. State cleanup / TTL
- Clear per-key state after emission.
- Additionally configure **State TTL** (or a cleanup timer) so that jobs that never terminate do not accumulate state indefinitely.

#### F. Worked example (largest stage per job)
Given SUBMIT times (minutes): `0, 2, 9, 19, 20` with `gap=10`:
- Stage1: `0,2,9` (since 9-2 < 10) => count=3
- Stage2: `19,20` (since 19-9 >= 10 starts new stage) => count=2
Result: `maxStageCount = 3` (emit only after terminal job event observed).

## Performance Targets

**Batch Pipeline Execution:**
- P50 latency: < 5 minutes (hourly pipelines)
- P95 latency: < 15 minutes
- Success rate: > 99%
- Data freshness: < 1 hour behind source

**Streaming Pipeline Execution:**
- Throughput: 10K+ events/second sustained
- End-to-end latency: P99 < 1 second
- Consumer lag: < 10K records behind
- Exactly-once delivery: Zero duplicates or losses

**Data Quality (Batch):**
- Quality score: > 95%
- Completeness: > 99%
- Timeliness: < 2 hours data lag
- Zero critical failures

**Streaming Quality:**


- **Cardinality validation:** In gated/terminal-driven queries, validate output cardinality: number of output rows should match the count of keys with qualifying terminal events (and, if required, at least one SUBMIT). Any extra rows typically indicate wrong terminal filtering, premature timers (watermarks), or emitting default zeros.
- Data freshness: P95 < 5 minutes from event generation
- Late data rate: < 5% outside watermark window
- Dead letter queue rate: < 1%
- Schema compatibility: 100% backward/forward compatible changes

**Cost Efficiency:**
- Cost per GB processed: < $0.10
- Cloud cost trend: Stable or decreasing
- Resource utilization: > 70%
