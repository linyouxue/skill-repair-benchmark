<label>Sandbox path access violation</label>

<first_observable_failure>
The first observable failure is an inability to load the provided evidence files: tool calls to `read_file` fail with “path escapes the allowed project root” and “file not found”. This prevents any inspection of the execution trace, verifier evidence, and skill rules, and explains the empty Output inventory.
</first_observable_failure>

<trajectory_step_that_produced_it>
At the initial evidence-gathering step (attempting to read `trace.jsonl`, `result.json`, `verifier/summary.json`, and `skill.md`), the agent used absolute paths outside the sandbox’s allowed root and then attempted a relative `trace.jsonl` that does not exist in the working directory.
</trajectory_step_that_produced_it>

<relevant_skill_rule_or_missing_rule>
This is not a domain skill/planning/control failure. It is a harness/sandbox constraint issue: the workflow lacks (or did not follow) a rule like “Only access files within the allowed project root; use the task-provided relative paths under the sandbox output directory; do not use host-machine absolute paths.”
</relevant_skill_rule_or_missing_rule>

<general_corrective_behavior>
Treat this as a non-skill-controllable environment error. Correct behavior is to:
1) Discover the sandbox root (e.g., by listing current directory or using only relative paths that the harness exposes), and
2) Read evidence via sandbox-local relative paths (copying/relocating files into the allowed root if needed), rather than referencing external absolute locations.
Do not attempt skill edits until trace/verifier artifacts are accessible.
</general_corrective_behavior>
