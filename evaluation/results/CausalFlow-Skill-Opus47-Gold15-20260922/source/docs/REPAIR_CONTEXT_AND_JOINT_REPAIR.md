# 基于依赖图的可靠修复与多步骤联合修复

> 状态：局部修复证据包已接入并完成全部17道 MBPP 历史联合候选的真实测试；联合执行器尚未实现。

## 1. 当前问题

CausalFlow 现在针对每个原因步骤独立生成若干候选，然后从该步骤向后重新执行。现有提示主要包含题目、错误答案、全部前序步骤和执行日志，存在四个问题：

1. 前序步骤很多，但没有突出目标步骤真正依赖的输入；
2. 没有明确给出目标步骤的直接下游、测试约束和后续失败证据；
3. 多个候选使用几乎相同的提示，模型容易重复同一种修改；
4. 多个原因步骤彼此关联时，系统仍分别修改，不能表达“两个修改必须同时成立”。

## 2. 已完成的第一步改进

新增 `repair_context.py`，在生成候选前构造有界的局部证据包：

| 信息 | 用途 |
| --- | --- |
| 直接输入步骤 | 告诉模型该步骤依据了什么，而不是塞入整条历史。 |
| 直接下游步骤 | 说明修改必须满足哪些后续使用要求。 |
| 任务约束与测试 | 对代码任务提供函数入口、测试和题目要求。 |
| 下游失败证据 | 提供断言、异常、失败工具返回或错误最终结果。 |
| 文件与状态读写 | 约束修改不能破坏已有资源关系。 |
| 其他原因步骤 | 提醒模型当前可能需要联合修复，不能宣称单点修改一定充分。 |
| 以前生成过的候选及结果 | 后续候选必须换一种错误假设或修改方式，减少重复。 |
| 图上的预计重放范围 | 让后续调度只重放可能受影响的部分；证据不足时回退完整重放。 |

该证据包不包含标准答案，因此可以直接用于“不向模型泄露标准答案”的主实验。`CounterfactualRepair` 已接入该证据包，并要求第2、3个候选避开前面已经尝试的修改。

同时修复了一个确定的计数错误：原代码会把“空的成功修复列表”也当作一个成功步骤；现在只统计非空成功列表。

候选输出现在还必须先说明错误原因、输出要求和输入输出规律。对代码测试，执行器会在不重复调用待测函数的前提下，把简单相等断言的失败信息补成“实际值/期望值”，供下一候选纠正。系统会拒绝空修改、原样返回和重复候选，最多重新生成3次。

## 3. 多步骤联合修复应如何实现

不应直接枚举所有原因步骤的全部组合，组合数会指数增长。建议采用分层搜索：

1. **先做增强后的单步修复。**每个原因步骤生成3个有差异的候选并真实重放。
2. **只对单步全部失败的样本进入联合阶段。**当前数据中有48道候选题，其中30道只有两个原因步骤，适合作为第一批实验。
3. **依赖图负责缩小组合。**优先组合存在直接依赖、共享同一资源或共同影响同一验证结果的步骤；第一版最多同时修改2步，必要时再扩到3步。
4. **一次生成一个原子修改集合。**模型输出必须包含每个步骤的修改、使用的证据、两个修改如何配合，以及为何单独修改不足。
5. **从最早修改点恢复，但只重放联合后代。**两个修改的重放范围取各自后代的并集；输出未变化时停止传播。
6. **最终结果必须通过真实测试。**开发阶段同时运行局部重放和完整重放；两者不一致时自动采用完整结果，并把样本加入漏依赖回归集。

联合执行需要新增一个明确接口：

```python
run_with_interventions(
    interventions={step_id: repaired_step, ...},
    replay_step_ids=[...],
    fallback_to_full=True,
)
```

这里不能简单把两个修改后的旧步骤塞进历史再继续执行，因为第一个修改可能改变两个步骤之间的中间状态。正确做法是在重放过程中按照稳定的步骤或资源标识依次应用修改；如果步骤无法稳定对齐，则回退完整重放。

## 4. 已找到的实验样本

`experiments/joint_repair_candidates/joint_repair_candidates.json` 中共有48道去重候选：

| 数据集 | 数量 |
| --- | ---: |
| GSM8K | 25 |
| MBPP | 17 |
| MedBrowseComp | 4 |
| SealQA | 2 |

最常见的两步组合是“规划/推理步骤 + 代码生成步骤”，共16道。这类任务适合检验：只改规划是否会重新生成正确代码、只改代码是否已经足够，以及两者同时修改是否才稳定通过。

这些样本只能称为“联合修复候选”，不能直接声称必须修改多步。因为现有单步失败也可能只是候选质量差。增强单点复测已排除13道 MBPP，当前剩35道：GSM8K 25、MBPP 4、MedBrowseComp 4、SealQA 2。严格判定仍须完成三组对照：旧单步提示、增强单步提示、增强联合修复。

## 5. 小规模实验设计

对30个双原因样本先选择10个可确定重放的 GSM8K/MBPP 任务，固定同一模型、温度和每步候选数：

| 组别 | 给模型的信息 | 修改方式 |
| --- | --- | --- |
| 基线 | 原提示 | 独立单步 |
| 上下文增强 | 局部证据包 | 独立单步 |
| 联合修复 | 局部证据包 + 另一原因步骤 + 失败候选 | 两步原子修改 |

主要指标：真实测试通过率、有效候选比例、重复候选率、平均候选次数、模型调用量、重放步骤数和实际时间。联合修复只有在通过率提升且完整/局部重放一致时才算有效。

## 6. 当前最合理的下一步

1. 先为候选增加函数参数、输出类型和“诊断—代码一致性”检查；
2. 在4道固定提示失败的 MBPP 任务上重跑增强单点，并为仍失败样本实现“两步定时干预执行器”；
3. 用依赖图后代并集做局部重放，并始终与完整重放对照；
4. 若两步联合修复没有明显优于增强单步修复，就不要扩大组合搜索，而应继续改进原因定位和候选证据。

## 7. 十七道真实代码题探索

从48道联合修复候选中选择4道 MBPP 题，使用 `google/gemini-2.5-flash-lite`，不向模型提供标准答案；每个候选都用原始测试在 Docker 中执行。上下文设计是在观察失败后逐步开发的，因此结果用于发现机制，不能当作无偏的通过率比较。

| 题目 | 旧/早期上下文 | 当前上下文 | 关键缺失信息 |
| --- | ---: | ---: | --- |
| MBPP-643 | 0/3 | 3/3 | 测试要求返回固定字符串，而不是布尔值。 |
| MBPP-73 | 未做配对基线 | 3/3 | 明确测试断言后可直接修正代码。 |
| MBPP-75 | 0/3 | 3/3 | 必须先写清输出类型和格式，再生成修改。 |
| MBPP-81 | 多轮均为0/3 | 1/1 | 必须写出“按较长输入长度、较短输入循环取值”的规律；当前只保留了1个不重复候选，另外两个候选槽因重复或无效被拒绝。 |

MBPP-643 的早期3个候选只改正则表达式，仍返回布尔值；突出测试断言和输出格式后，3个候选全部通过。MBPP-81 更能说明信息层次：模型一度能用文字说出“较短输入要循环”，但代码仍用截断或空值补齐；强制给出行为规律并反馈断言的实际值/期望值后，才生成按模运算循环取值的正确代码。

这4道题在历史结果中都满足“至少两个原因步骤、没有成功的旧单步修复”，但增强上下文后只修改代码步骤即可通过。因此，历史单步候选失败不能直接证明必须联合修复；候选质量是重要混杂因素。

在提示规则固定为当前版本后，又一次性跑完剩余13道 MBPP 历史候选，不再按题目修改提示：

| 固定提示结果 | 题目数 | 题号 |
| --- | ---: | --- |
| 至少一个单点候选通过 | 9 | 277、295、344、485、486、576、860、898、926 |
| 所有单点候选失败 | 4 | 288、584、597、620 |

13道题共要求39个候选槽；去除空修改和重复修改后实际保留24个不同候选，其中12个通过。总运行时间约298秒。一次随机运行仍不能给出稳定通过率，但这批数据没有逐题调提示，能用于选择下一批实验：4道固定提示失败题应优先进入两步联合修复；9道已通过题不再用于证明联合必要性。

对4道失败题用增强断言再次执行已有候选后，错误已更具体：MBPP-288 和 597 接受额外参数后仍误解参数含义；MBPP-584 已识别期望字符串，却仍返回只含一个字符串的列表；MBPP-620 识别到第二个参数但补丁仍只接收一个参数。这表明下一层瓶颈是“诊断文字正确但补丁没有落实诊断”，不应立刻归因于必须修改规划步骤。联合实验前应增加静态契约检查：函数参数个数、输出外层类型和诊断中声明的行为必须与补丁一致，不一致的候选直接重采样。

综合两阶段结果，17道 MBPP 候选中13道已有增强单点成功，48道历史候选剩35道尚未排除。正式结论仍需要固定随机性并重复运行，对照旧单点、增强单点和联合修复三组。
